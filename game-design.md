# Keyboard Mages — Game Design & Architecture Document

> Этот файл предназначен для использования как `CLAUDE.md` / контекстный документ проекта.
> Содержит игровой дизайн, архитектурные решения и открытые вопросы, обсуждённые на этапе планирования.

## 1. Концепция

Браузерная PvP-игра "Keyboard Mages". Игроки сражаются в дуэли 1v1, выбирая заклинания.
Чтобы заклинание применилось, игрок должен быстро и правильно ввести комбинацию символов
(слово-триггер) на клавиатуре. После корректного и своевременного ввода заклинание срабатывает.

## 2. Технологический стек

- **Backend:** NestJS, WebSocket Gateway (Socket.IO), состояние боя — в памяти сервера (source of truth)
- **Frontend:** Angular (UI-оболочка: меню, лобби, HUD, RxJS/Signals для состояния)
- **Боевая сцена / рендер:** PixiJS (спрайты, партиклы) + GSAP (твининг эффектов, тряска экрана и т.п.)
- **Связь:** WebSocket-протокол, сервер валидирует весь игровой ввод

## 3. Архитектура backend (NestJS)

Ключевые модули:
- `MatchmakingModule` — очередь на поиск соперника, создание matchId, пары игроков
- `DuelGateway` — WebSocket-события: `join`, `cast_attempt`, `key_input`, `disconnect`
- `DuelService` — состояние боя в памяти (HP, активные касты, кулдауны, активные эффекты)
- `SpellsModule` — реестр заклинаний (school, tier, type, trigger word, эффекты)
- `EffectsService` — начисление/тик/снятие баффов и дебаффов (см. раздел 6)

### Протокол WebSocket-событий (черновик)

```
client -> server: cast_start (spellId)
client -> server: key_input (char, timestamp)   // посимвольно, для live-эффекта у соперника
server -> client: input_ack (correct: bool, progress)
server -> both:   spell_resolved (success, damage, timeTaken)
server -> both:   effects_sync { playerId, effects: [{ type, remainingMs, magnitude }] }
```

**Принципиально:** вся валидация ввода (правильность и скорость) происходит на сервере.
Сервер сам фиксирует momент получения каждого символа (arrival time WebSocket-сообщения),
клиентским timestamp'ам для расчёта результата не доверяем.

## 4. Защита от программного/бот-ввода

- **`KeyboardEvent.isTrusted`** — фильтровать на клиенте события с `isTrusted: false`
  (защищает от JS-инъекций/автоматизации внутри страницы, но не от аппаратных эмуляторов/макросов уровня ОС)
- **Серверные тайминги** — время каста считается по времени получения сообщений сервером, не по клиентским меткам
- **Анализ вариативности интервалов** — слишком равномерные интервалы между нажатиями = признак бота;
  считать дисперсию, флагать аномально низкую вариативность
- **Порог физической скорости** — жёсткий кап (~15-20 нажатий/сек), выше — режект/флаг
- **Накопительная репутация** — не банить за одно подозрительное действие, копить anomaly score за сессию/матчи

## 5. Система заклинаний

### 5.1 Три оси классификации
Каждое заклинание характеризуется: **название**, **описание**, **школа**, **тип**, **уровень сложности**.

### 5.2 Уровни сложности

| Уровень | Длина триггера | Кулдаун | Окно на ввод | Мощь |
|---|---|---|---|---|
| 1 (Базовый) | 4–6 символов | 3–6 сек | ~1.5–2 сек | Низкая, доступна часто |
| 2 (Продвинутый) | 7–10 символов | 10–15 сек | ~2.5–3.5 сек | Средняя, тактическая |
| 3 (Ультимативный) | 11–16 символов | 25–40 сек | ~4–6 сек | Высокая, решающая |

Окно на ввод рекомендуется завязывать на целевой WPM, а не на фиксированное время,
чтобы не дискриминировать медленно печатающих игроков.

### 5.3 Типы

- **Атака (Attack)** — прямой урон, часто с доп. эффектом
- **Защита (Defense)** — щиты, снижение урона, отражение
- **Поддержка (Support)** — хил, баффы, дебаффы, контроль, изменение кулдаунов

## 6. Система эффектов (баффы/дебаффы)

### 6.1 Модель данных

```typescript
interface ActiveEffect {
  id: string;                 // uuid инстанса каста
  effectType: EffectType;     // 'damage_boost' | 'slow' | 'dot' | 'hot' | 'shield' | 'silence' | 'cooldown_reduction'
  sourceSpellId: string;
  targetPlayerId: string;
  magnitude: number;          // сила эффекта (%, флэт, множитель)
  durationMs: number;
  appliedAt: number;          // серверный timestamp
  tickIntervalMs?: number;    // для DoT/HoT
}
```

### 6.2 Правило стакинга (зафиксировано)

- Длительность дебаффа/баффа не превышает кулдаун заклинания, которое его накладывает
  → самоперекрытие одного и того же заклинания невозможно физически
- Эффекты **разных** заклинаний (в т.ч. с одинаковым `effectType`) тикают **параллельно**,
  идентифицируются по `sourceSpellId`/`instanceId`, а не по типу эффекта
- Стакинг всегда `stack` — отдельная логика `refresh`/`ignore` не нужна
- Единственное условие удаления эффекта — истечение `durationMs`

### 6.3 Комбинирование модификаторов — МУЛЬТИПЛИКАТИВНО

Зафиксировано решение: при наложении нескольких однотипных эффектов (например, несколько
источников замедления) они комбинируются мультипликативно, а не аддитивно — чтобы избежать
"лока" игрока при 3-4 одновременных дебаффах (естественное затухание отдачи).

```typescript
function getEffectiveCastWindow(base: number, effects: ActiveEffect[]): number {
  const slowEffects = effects.filter(e => e.effectType === 'slow');
  const multiplier = slowEffects.reduce((acc, e) => acc * (1 + e.magnitude), 1);
  return base * multiplier;
}
```

Аналогично применяется для `damage_boost`, `cooldown_reduction` и т.д. — всегда произведение
модификаторов, не сумма.

### 6.4 Тикающий цикл боя

Общий heartbeat на сервере (например, `setInterval` раз в 250-500мс на матч):
- применяет DoT/HoT по `tickIntervalMs`
- проверяет истечение `durationMs`, удаляет истёкшие эффекты
- пересчитывает эффективные модификаторы (урон, cast window, доступность каста)
- рассылает `effects_sync` клиентам

Клиент только отображает присланное состояние (иконки баффов с таймером), не считает
логику истечения самостоятельно.

## 7. Решённые вопросы дизайна

1. **Контрольные эффекты (рут/заморозка/тишина)** — отдельного `Spell.type` не вводим.
   Контроль остаётся тегом на уровне `ActiveEffect.effectType` (`slow`/`silence`/будущий `root`
   и т.д.), а `Spell.type` (Attack/Defense/Support) описывает роль заклинания в бою, а не наличие
   контроля как побочного эффекта. Уже соответствует реализации в `backend/src/effects/effect.types.ts`.
2. **Слова-триггеры** — остаются тематическими английскими словами (ростер раздела 5.4).
   Приоритет отдан фэнтези-погружению над абсолютной языковой нейтральностью замера скорости
   печати; это осознанный компромисс, типичный для жанра typing-race.
3. **Штраф за опечатку** — полный сброс прогресса каста (реализовано в
   `DuelService.handleKeyInput`, `backend/src/duel/duel.service.ts`). Осознанный риск: одна
   опечатка на 15-м символе 16-символьного ultimate-триггера обнуляет весь каст — держим в уме
   как кандидата на пересмотр после первых игровых тестов баланса заклинаний уровня 3.
4. **Синергии школ / комбо-заклинания** — отложены за пределы MVP (см. раздел 8). Базовый
   боевой цикл (25 заклинаний + система эффектов) должен быть играбелен и протестирован до того,
   как добавлять систему комбо между двумя игроками.

## 8. Открытые вопросы (отложено)

1. UI-группировка одинаковых по смыслу эффектов от разных источников (единая иконка с "×N"
   vs отдельные иконки на портрете) — решим при проектировании HUD эффектов на клиенте.
2. Визуальные ассеты (иконки заклинаний, спрайты персонажей) — вопрос ресурсов
   (художник / генератор изображений с img2img / готовый ассет-пак), не архитектуры.
   Вернёмся при переходе к боевой сцене (PixiJS).
3. Синергии школ / комбо-заклинания (Лёд + Хаос и т.п., см. решение в разделе 7.4) — фаза 2,
   после того как базовая боевая петля проверена в игре.
