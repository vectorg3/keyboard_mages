# Keyboard Mages — Game Design & Architecture Document

> Этот файл предназначен для использования как `CLAUDE.md` / контекстный документ проекта.
> Содержит игровой дизайн, архитектурные решения и открытые вопросы, обсуждённые на этапе планирования.

## 1. Концепция

Браузерная PvP-игра "Keyboard Mages". Игроки сражаются в дуэли 1v1, выбирая заклинания.
Чтобы заклинание применилось, игрок должен быстро и правильно ввести комбинацию символов
(слово-триггер) на клавиатуре. После корректного и своевременного ввода заклинание срабатывает.

## 2. Технологический стек

- **Backend:** NestJS, WebSocket Gateway (Socket.IO), состояние боя — в памяти сервера (source of truth)
- **Frontend:** Angular (UI-оболочка: меню, лобби, HUD, RxJS/Signals для состояния)
- **Боевая сцена / рендер:** PixiJS (спрайты, партиклы) + GSAP (твининг эффектов, тряска экрана и т.п.)
- **Связь:** WebSocket-протокол, сервер валидирует весь игровой ввод

## 3. Архитектура backend (NestJS)

Ключевые модули:
- `MatchmakingModule` — очередь на поиск соперника, создание matchId, пары игроков
- `DuelGateway` — WebSocket-события: `join`, `cast_attempt`, `key_input`, `disconnect`
- `DuelService` — состояние боя в памяти (HP, активные касты, кулдауны, активные эффекты)
- `SpellsModule` — реестр заклинаний (school, tier, type, trigger word, эффекты)
- `EffectsService` — начисление/тик/снятие баффов и дебаффов (см. раздел 6)

### Протокол WebSocket-событий (черновик)

```
server -> both:   match_countdown { remainingMs }         // раз в тик, пока матч ещё не начался
server -> both:   match_started { startedAt }             // один раз, когда истекла пауза после match_found
client -> server: cast_start (spellId)
client -> server: key_input (char, timestamp)   // посимвольно, для live-эффекта у соперника
server -> client: input_ack (correct: bool, progress)
server -> both:   spell_resolved (success, damage, timeTaken)
server -> both:   effects_sync { playerId, effects: [{ type, remainingMs, magnitude }] }
```

**Принципиально:** вся валидация ввода (правильность и скорость) происходит на сервере.
Сервер сам фиксирует momент получения каждого символа (arrival time WebSocket-сообщения),
клиентским timestamp'ам для расчёта результата не доверяем.

## 4. Защита от программного/бот-ввода

- **`KeyboardEvent.isTrusted`** — фильтровать на клиенте события с `isTrusted: false`
  (защищает от JS-инъекций/автоматизации внутри страницы, но не от аппаратных эмуляторов/макросов уровня ОС)
- **Серверные тайминги** — время каста считается по времени получения сообщений сервером, не по клиентским меткам
- **Анализ вариативности интервалов** — слишком равномерные интервалы между нажатиями = признак бота;
  считать дисперсию, флагать аномально низкую вариативность
- **Порог физической скорости** — жёсткий кап (~15-20 нажатий/сек), выше — режект/флаг
- **Накопительная репутация** — не банить за одно подозрительное действие, копить anomaly score за сессию/матчи

## 5. Система заклинаний

### 5.1 Три оси классификации
Каждое заклинание характеризуется: **название**, **описание**, **школа**, **тип**, **уровень сложности**.

### 5.2 Уровни сложности

| Уровень | Длина триггера | Кулдаун | Окно на ввод | Мощь |
|---|---|---|---|---|
| 1 (Базовый) | 4–6 символов | 3–6 сек | ~1.5–2 сек | Низкая, доступна часто |
| 2 (Продвинутый) | 7–10 символов | 10–15 сек | ~2.5–3.5 сек | Средняя, тактическая |
| 3 (Ультимативный) | 11–16 символов | 25–40 сек | ~4–6 сек | Высокая, решающая |

Окно на ввод рекомендуется завязывать на целевой WPM, а не на фиксированное время,
чтобы не дискриминировать медленно печатающих игроков.

Урон Attack-заклинаний в таблицу не входит: он не выводится из тира, а задаётся
диапазоном `[min, max]` индивидуально на каждом заклинании (`Spell.damage`, раздел 7.6) —
конкретные числа см. в `backend/src/spells/spell-roster.ts`.

### 5.3 Типы

- **Атака (Attack)** — прямой урон, часто с доп. эффектом
- **Защита (Defense)** — щиты, снижение урона, отражение
- **Поддержка (Support)** — хил, баффы, дебаффы, контроль, изменение кулдаунов

## 6. Система эффектов (баффы/дебаффы)

### 6.1 Модель данных

```typescript
interface ActiveEffect {
  id: string;                 // uuid инстанса каста
  effectType: EffectType;     // 'damage_boost' | 'slow' | 'dot' | 'hot' | 'shield' | 'silence' | 'cooldown_reduction'
  sourceSpellId: string;
  targetPlayerId: string;
  magnitude: number;          // сила эффекта (%, флэт, множитель)
  durationMs: number;
  appliedAt: number;          // серверный timestamp
  tickIntervalMs?: number;    // для DoT/HoT
}
```

### 6.2 Правило стакинга (зафиксировано)

- Длительность дебаффа/баффа не превышает кулдаун заклинания, которое его накладывает
  → самоперекрытие одного и того же заклинания невозможно физически
- Эффекты **разных** заклинаний (в т.ч. с одинаковым `effectType`) тикают **параллельно**,
  идентифицируются по `sourceSpellId`/`instanceId`, а не по типу эффекта
- Стакинг всегда `stack` — отдельная логика `refresh`/`ignore` не нужна
- Единственное условие удаления эффекта — истечение `durationMs`

### 6.3 Комбинирование модификаторов — МУЛЬТИПЛИКАТИВНО

Зафиксировано решение: при наложении нескольких однотипных эффектов (например, несколько
источников замедления) они комбинируются мультипликативно, а не аддитивно — чтобы избежать
"лока" игрока при 3-4 одновременных дебаффах (естественное затухание отдачи).

```typescript
function getEffectiveCastWindow(base: number, effects: ActiveEffect[]): number {
  const slowEffects = effects.filter(e => e.effectType === 'slow');
  const multiplier = slowEffects.reduce((acc, e) => acc * (1 + e.magnitude), 1);
  return base * multiplier;
}
```

Аналогично применяется для `damage_boost`, `cooldown_reduction` и т.д. — всегда произведение
модификаторов, не сумма.

### 6.4 Тикающий цикл боя

Общий heartbeat на сервере (например, `setInterval` раз в 250-500мс на матч):
- применяет DoT/HoT по `tickIntervalMs`
- проверяет истечение `durationMs`, удаляет истёкшие эффекты
- пересчитывает эффективные модификаторы (урон, cast window, доступность каста)
- рассылает `effects_sync` клиентам

Клиент только отображает присланное состояние (иконки баффов с таймером), не считает
логику истечения самостоятельно.

## 7. Решённые вопросы дизайна

1. **Контрольные эффекты (рут/заморозка/тишина)** — отдельного `Spell.type` не вводим.
   Контроль остаётся тегом на уровне `ActiveEffect.effectType` (`slow`/`silence`/будущий `root`
   и т.д.), а `Spell.type` (Attack/Defense/Support) описывает роль заклинания в бою, а не наличие
   контроля как побочного эффекта. Уже соответствует реализации в `backend/src/effects/effect.types.ts`.
2. **Слова-триггеры** — остаются тематическими английскими словами (ростер раздела 5.4).
   Приоритет отдан фэнтези-погружению над абсолютной языковой нейтральностью замера скорости
   печати; это осознанный компромисс, типичный для жанра typing-race.
3. **Штраф за опечатку** — полный сброс прогресса каста (реализовано в
   `DuelService.handleKeyInput`, `backend/src/duel/duel.service.ts`). Осознанный риск: одна
   опечатка на 15-м символе 16-символьного ultimate-триггера обнуляет весь каст — держим в уме
   как кандидата на пересмотр после первых игровых тестов баланса заклинаний уровня 3.
4. **Синергии школ / комбо-заклинания** — отложены за пределы MVP (см. раздел 8). Базовый
   боевой цикл (25 заклинаний + система эффектов) должен быть играбелен и протестирован до того,
   как добавлять систему комбо между двумя игроками.
5. **Пауза перед стартом боя** — матч начинается не сразу по `match_found`, а спустя
   3 секунды (`DuelService.PRE_MATCH_DELAY_MS`, `MatchState.startsAt`). До этого момента
   `DuelGateway` рассылает `match_countdown { remainingMs }` вместо боевого тика, а
   `DuelService.startCast` отклоняет любые касты с `reason: 'match_not_started'`. По истечении
   паузы один раз уходит `match_started`, и обычный heartbeat (эффекты/касты) включается.
6. **Урон Attack-заклинаний — диапазон, не значение по тиру.** Каждое Attack-заклинание
   задаёт собственный `damage: { min, max }` (`backend/src/spells/spell.types.ts`), фактический
   урон бросается случайно в этом диапазоне при разрешении каста (`DuelService.rollDamage`).
   Заклинания одного тира могут иметь разную мощь и разброс (например, Spark 6–8 против общего
   плейсхолдера Basic-урона). Заклинания, для которых индивидуальный диапазон ещё не откалиброван,
   временно используют старое фиксированное значение по тиру как flat-диапазон `[v, v]`
   (`PLACEHOLDER_DAMAGE_BY_TIER` в `spell-roster.ts`) — предмет дальнейшей балансировки.
   Дополнительно заклинание может объявить `Spell.onHitEffect` — эффект, накладываемый при
   успешном попадании независимо от типа заклинания, по умолчанию на соперника кастера
   (например, Blaze: поджог `dot` 2 урона/тик на 3 сек вместе с уроном; Winter's Grasp:
   `cooldown_reduction` с положительным `magnitude` — Support-заклинание без урона, которое
   замедляет восстановление кулдауна соперника), либо на самого кастера через `target: 'self'`
   (Frozen Armor, см. п.8). Знак `magnitude` для мультипликативных типов эффекта (`slow`,
   `damage_boost`, `cooldown_reduction`) значим: положительный усиливает/удлиняет базовую
   величину, отрицательный ослабляет/сокращает (см. `EffectsService.combinedMultiplier`,
   формула `base * (1 + magnitude)`). `EffectType: 'silence'` (блокировка конкретного
   `spellId` — не путать с заклинанием Power Rune, бывш. Silence, раздел 7.14, которое давно
   переделано в самобаф урона и с этим типом эффекта не связано) и хил — свои эффекты
   Support-заклинаний, которые generic `onHitEffect` пока не покрывает и которые остаются
   открытым вопросом (см. TODO в `DuelService.buildResolution`).
7. **Эффекты, зависящие от навыка игрока, — избегаем.** Изначальная идея Ice Shard
   ("шанс скрыть подсказку ввода на 1 сек") отклонена: скрытие подсказки не мешает опытному
   игроку, печатающему по памяти, и наказывает только новичков — обратный от желаемого эффект
   баланса. Заменено на гарантированный (не по шансу) `slow`, как у Frostbite — работает
   одинаково независимо от того, смотрит ли игрок на подсказку. Держим это как общий принцип
   при добавлении будущих эффектов: приоритет отдаём тем, что бьют по объективному игровому
   состоянию (время, HP, кулдауны), а не по UI-подсказкам, которые опытные игроки не используют.
8. **Щит (Frozen Armor) — отдельный конвейер урона, не сводится к multiplier-эффектам.**
   `effectType: 'shield'` использует `magnitude` как флэт-пул HP (не множитель): при входящем
   Attack-уроне (`DuelService.buildResolution`) сначала вызывается
   `EffectsService.absorbWithShields`, которая списывает урон с активных щитов цели по очереди
   создания, пока урон не закончится или щиты не исчерпаются; остаток идёт по HP как обычно.
   "Лёгкое отражение" — доля поглощённого (не входящего) урона, `ActiveEffect.reflectRatio`
   (0.2 у Frozen Armor), возвращается атакующему как урон по его HP. Щит вешается на самого
   кастера (`onHitEffect.target: 'self'`) и живёт `durationMs`, даже если не исчерпан за это
   время — как и другие эффекты, снимается общим `pruneExpired`.
9. **Ember Ward — процентное снижение входящего урона, без нового `effectType`.**
   Вместо отдельного "damage_reduction" переиспользуем `'damage_boost'`: `magnitude`
   по-прежнему множитель `(1 + magnitude)` для урона, но у Ember Ward он навешивается на
   самого кастера (`onHitEffect.target: 'self'`) с отрицательным значением (`-0.25` → урон
   ×0.75 на 1.5 сек). `DuelService.buildResolution` теперь считает `getEffectiveDamage` сразу
   по объединению эффектов атакующего И цели — баффы атакующего (положительный `magnitude`)
   и защита цели (отрицательный) комбинируются в одном мультипликативном проходе. В отличие
   от Frozen Armor это не отдельный пул HP: пока эффект активен, он ослабляет весь входящий
   урон, а не тратится за один удар. `durationMs` (1500) намеренно короче `cooldownMs`
   Basic-тира (2000) — иначе перекаст держал бы 25%-снижение урона 100% времени боя.
10. **Кулдаун общий на весь тир внутри школы, а не на конкретное заклинание.** Успешный каст
    любого заклинания ставит на кулдаун ВСЕ заклинания той же школы и того же тира
    (`SpellsService.getTierMates`, `DuelService.buildResolution`) — например, Inferno Storm
    (Fire, Ultimate) кладёт на кулдаун и себя, и Phoenix Rebirth (Fire, Ultimate), но не
    трогает Ultimate-заклинания других школ. Явно НЕ глобально по всем школам: игрок будет
    выбирать школу мага перед поиском матча и сможет кастовать только заклинания этой школы
    (см. открытый вопрос ниже) — на практике "весь тир школы" и есть "все доступные игроку
    заклинания этого тира". Сейчас `DuelService.startCast` ещё не ограничивает `spellId` по
    выбранной школе — это отдельная задача, без неё игрок технически может запросить любой
    `spellId` из ростера независимо от выбранного мага. *(Обновление после раздела 7.12: выбор
    школы теперь ХРАНИТСЯ на сервере как `PlayerState.school`, но `startCast` его всё ещё не
    проверяет — см. открытый вопрос ниже.)*
11. **Phoenix Rebirth — мгновенный хил + одноразовое "не даёт умереть" (`death_ward`).**
    `Spell.healOnCast` (25) — прямое восстановление HP кастера в момент разрешения каста,
    отдельно от `onHitEffect`: не тикающий эффект, а мгновенное изменение, как урон у Attack.
    `onHitEffect: { type: 'death_ward', target: 'self', magnitude: 1, durationMs: 4000 }` —
    пока активен, следующий смертельный удар не убивает кастера, а оставляет его с `magnitude`
    HP и расходует эффект (одноразовый). Реализовано через единый `DuelService.applyDamage()`,
    через который теперь проходит **весь** урон по HP (прямой удар, отражение щитом, DoT-тик) —
    это нужно, чтобы death_ward одинаково спасал от любого источника урона, а не только от
    прямого попадания Attack-заклинания. `durationMs` (4000) короче `cooldownMs` Ultimate-тира
    (6000) по той же причине, что и у Ember Ward — не давать перманентный аптайм эффекта.
12. **`PlayerState.school` — школа мага хранится на сервере (осталась после ревизии п.14).**
    Изначально понадобилась для старой версии Power Rune/Spellbreaker ("случайное заклинание
    школы соперника" — см. историю ревизий п.14), которая позже была пересмотрена и от этой
    зависимости отказалась. Поле и вся прокладка НЕ убраны, а намеренно оставлены: это
    единственная реализованная часть открытого вопроса раздела 8 п.4 (сервер должен знать
    школу игрока, чтобы позже ограничить, какие `spellId` он может кастовать) — было бы
    странно выкидывать её только для того, чтобы вскоре добавить заново. Прокинуто через весь
    matchmaking-путь: `FindMatchPayload.school` → `MatchmakingService.enqueue(playerId,
    school)` → `DuelService.createMatch(playerAId, playerASchool, playerBId, playerBSchool)` →
    `PlayerState.school`. Фронтенд пока этот payload не отправляет. `startCast` пока НЕ
    проверяет `spell.school === player.school` — само ограничение всё ещё не реализовано
    (раздел 8, п.4).
13. **Arcane Missile игнорирует ЧУЖУЮ защиту, но не щиты.** `Spell.ignoresDamageReduction`
    убирает эффекты ЦЕЛИ (`this.effectsOn(match, targetId)`) из расчёта `getEffectiveDamage` —
    то есть обходит именно вещи вроде Ember Ward (`damage_boost` с отрицательным `magnitude`
    на самой цели). Щиты (`shield`, Frozen Armor) — отдельный конвейер (`absorbWithShields`,
    п.8) и им не затрагиваются: Arcane Missile всё ещё можно заблокировать щитом, только не
    процентным снижением урона. Осознанное сужение "части защиты" из исходного описания.
14. **Power Rune / Spellbreaker — ревизия основной механики: баф исходящего урона себе, а НЕ
    кулдаун случайному заклинанию соперника.** Первая версия (`Spell.disableRandomSpell:
    { durationMs }`, `DuelService.disableRandomSchoolSpell`, `SpellsService.getBySchool`) при
    успехе кастера ставила на кулдаун случайное заклинание ИЗ ШКОЛЫ ЦЕЛИ. Полностью заменена
    (весь код и типы удалены, не оставлено закомментированным) на самобаф через обычный
    `onHitEffect`: `{ type: 'damage_boost', target: 'self', damageDirection: 'outgoing' }` —
    Power Rune (бывш. Silence, `magnitude: 0.15`, 2 сек), Spellbreaker (`magnitude: 0.3`, 4 сек, вдобавок к
    урону 24–28). Использует уже существующий конвейер `damage_boost`/`damageDirection`
    (п.17) — новой инфраструктуры не потребовалось. `PlayerState.school` (п.12) для этой
    механики больше не нужен, но оставлен ради открытого вопроса раздела 8 п.4.
15. **`reflect` — новый `EffectType` для Mirror Shield, отдельно от `shield.reflectRatio`.**
    В отличие от щита Frozen Armor (одноразовый пул HP, реф ставится через
    `ActiveEffect.reflectRatio` и отражает долю от ПОГЛОЩЁННОГО щитом урона), `reflect` — это
    длящийся бафф без пула: пока активен (`durationMs`, 2.5 сек у Mirror Shield), КАЖДЫЙ
    полученный удар отражает `magnitude`-долю (0.2) обратно атакующему, не расходуясь и не
    снижая урон, который получает сам защищающийся. Считается уже после поглощения щитом, если
    оно тоже есть, чтобы не задваивать эффект от одного и того же удара.
16. **Time Warp — `resetsCooldownTiers`, включая собственный тир, с ожидаемым нюансом.**
    `Spell.resetsCooldownTiers: [Advanced, Ultimate]` обнуляет `cooldowns` всех заклинаний этих
    тиров своей школы ДО стандартного блока кулдауна (п.10). Так как Time Warp сам Ultimate,
    сброс тира 3 в рамках этого же каста визуально не заметен: стандартный блок сразу следом
    безусловно ставит кулдаун на весь Ultimate-тир заново (иначе получился бы бесплатный
    Time Warp без кулдауна вообще). Реальный эффект — только тир 2 (Advanced) освобождается.
    Оставлено как есть, а не убрано: намеренно соответствует дословной формулировке задачи,
    и не ломает баланс, раз тир 3 всё равно перезаписывается.
17. **`damage_boost` получил направление (`damageDirection: 'outgoing' | 'incoming'`) — задним
    числом исправлен скрытый баг Ember Ward.** До этого пункта единый механизм `damage_boost`
    комбинировал эффекты атакующего И цели в одном мультипликативном проходе без различия
    "чей это баф и на что он влияет" — из-за этого Ember Ward (магнитуда −0.25 на самом
    кастере) фактически ослаблял и ЕГО СОБСТВЕННЫЙ исходящий урон, пока щит активен, а не
    только входящий, как задумано. Понадобилось выявить и исправить при реализации Unstable
    Surge (раздел 5.4), где ровно этот же тип эффекта должен давать ДВА явно разных случайных
    исхода — "усиление исходящего" и "усиление входящего" — и без направления они были бы
    неотличимы. `DuelService.effectsForDamageRole(match, playerId, role)` фильтрует
    `damage_boost`-эффекты игрока по `damageDirection` перед передачей в `getEffectiveDamage`;
    отсутствие `damageDirection` трактуется как "действует в обе стороны" (обратная
    совместимость). Ember Ward обновлён (`damageDirection: 'incoming'`).
18. **`Spell.randomEffectPool` — как `onHitEffect`, но выбирается один случайный элемент.**
    Introduced для Unstable Surge и Chaotic Shield: при успешном касте `DuelService`
    выбирает ровно один элемент массива (`Math.random()`) и применяет его точно так же, как
    единственный `onHitEffect` — обобщено в одну переменную `chosenEffect` в
    `buildResolution`, обе схемы (фиксированный эффект и случайный пул) взаимоисключающи и
    делят один и тот же код применения.
19. **Unstable Surge — все 4 случайных исхода бьют по САМОМУ ЗАКЛИНАТЕЛЮ, включая два
    негативных.** Сопротивление (−30%, 2с) и усиление исходящего урона (+20%, 3с) — баффы;
    периодический урон себе (3/тик, 3 тика по 1с) и усиление ВХОДЯЩЕГО урона себе (+20%, 3с) —
    даунсайды. Осознанное расширение темы "нестабильная хаотичная магия может навредить и
    самому магу" (см. также Chaotic Shield, п.20) — заклинание с шансом самому себе навредить,
    а не только рандомный бафф.
20. **Chaotic Shield — "отражает заклинание" реализовано через shield с большим пулом
    (999) + `reflectRatio: 1`, а не отдельным одноразовым механизмом.** Технически это
    "поглощает и отражает всё, пока не потратит пул или не истекут 2 секунды", а не строго
    гарантированное "ровно одно заклинание" — если два вражеских удара попадут в это окно,
    оба будут поглощены и отражены. Выбрано намеренно как приближение без новой инфраструктуры
    (использует уже существующий `absorbWithShields` + `reflectRatio` из Frozen Armor/раздела
    7.8), при обычном темпе боя (кулдауны/окно каста) второй удар в те же 2 секунды
    маловероятен, но не невозможен.
21. **Void Collapse — `cooldown_delay`, новый `EffectType` для ФЛЭТ-добавки к кулдауну
    (не процент).** В отличие от `cooldown_reduction` (мультипликативный, `base * (1 +
    magnitude)`, см. Winter's Grasp/п.6), `cooldown_delay` — это прямая добавка в мс
    (`magnitude: 3000`) к `effectiveCooldown` следующего успешного каста ТОГО ЖЕ игрока.
    Процент не подошёл бы: одна и та же "штраф 3 секунды" даёт разный относительный эффект
    для разных тиров (150% для Basic-кулдауна 2000мс против 50% для Ultimate-кулдауна 6000мс).
    Реализовано как одноразовый расходуемый эффект (по аналогии с `death_ward`, раздел 7.11):
    `DuelService` считывает и СРАЗУ удаляет `cooldown_delay`-эффекты кастера в момент, когда
    ставит кулдаун за следующий успешный каст — гарантирует именно "следующее заклинание",
    а не "любое в течение X секунд". `durationMs` (15000) — просто защитный потолок на случай,
    если игрок долго не кастует ничего вообще.
22. **Механизм "кулдаун случайному заклинанию школы соперника" — возвращён, но уже для Nature,
    не Arcane.** В п.14 этот же механизм (`Spell.disableRandomSpell`,
    `DuelService.disableRandomSchoolSpell`, `SpellsService.getBySchool`) был полностью удалён
    после ревизии Power Rune/Spellbreaker. Ничего не пришлось изобретать заново концептуально —
    код восстановлен в точности как был (тот же файл истории git это покажет), только
    подключён к другим заклинаниям: Vine Whip (1 сек), Entangle (3 сек), Nature's Fury (5 сек).
    Значение `PlayerState.school` (п.12), которое было оставлено "про запас" именно на такой
    случай, теперь снова используется по прямому назначению.
23. **Bark Skin — дословная копия эффекта Ember Ward.** По прямому запросу: тот же
    `onHitEffect` (`damage_boost`, `target: 'self'`, `magnitude: -0.25`, `durationMs: 1500`,
    `damageDirection: 'incoming'`), что и у `fire_ember_ward`. Два разных заклинания разных школ
    с идентичной механикой — осознанно, не считается дублированием кода (баланс/тематика важнее
    DRY на уровне игровых данных).
24. **Vampiric Roots — новое Ultimate-заклинание Nature, добавленное по запросу без
    уточнённого названия.** Требование было "такой же диапазон урона, что и у Nature's Fury
    (28–32), но с HoT на заклинателя, исцеляющим на 3 ед. в течение 4 секунд" — имя и триггер
    (`vampiricroots`, 13 символов, укладывается в диапазон Ultimate-триггеров 11–16) придуманы
    по тематике "заклинание-вампир": урон противнику + жизнь себе. Тиковый интервал HoT (1 сек,
    итого 4 тика по 3 = 12 HP) принят по аналогии с Regrowth, которая явно описана как "3 ед.
    КАЖДУЮ секунду" — формулировка для Vampiric Roots не уточняла тик явно, интервал 1 сек
    выбран как разумное умолчание, а не единственно возможное прочтение.

## 8. Открытые вопросы (отложено)

1. UI-группировка одинаковых по смыслу эффектов от разных источников (единая иконка с "×N"
   vs отдельные иконки на портрете) — решим при проектировании HUD эффектов на клиенте.
2. Визуальные ассеты (иконки заклинаний, спрайты персонажей) — вопрос ресурсов
   (художник / генератор изображений с img2img / готовый ассет-пак), не архитектуры.
   Вернёмся при переходе к боевой сцене (PixiJS).
3. Синергии школ / комбо-заклинания (Лёд + Хаос и т.п., см. решение в разделе 7.4) — фаза 2,
   после того как базовая боевая петля проверена в игре.
4. Привязка выбора школы мага к серверному ограничению доступных `spellId` в
   `DuelService.startCast`. Школа теперь ХРАНИТСЯ на сервере (`PlayerState.school`, раздел 7.12,
   прокинута через matchmaking), но `startCast` её ещё не проверяет — игрок технически может
   кастовать заклинание чужой школы. Фронтенд тоже пока не отправляет реальный выбор школы в
   `find_match` (`App.youMageType`/`foeMageType` — по-прежнему хардкод, влияют только на спрайт).
   Важно доделать до того, как общий кулдаун по тиру (раздел 7.10) станет заметен игрокам как
   "фича", а не просто фоновая деталь реализации.
